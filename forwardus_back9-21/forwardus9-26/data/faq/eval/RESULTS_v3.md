## 3. 검색 방식 비교 (바꾸기 전에 쟀습니다)

튜닝 140문항 중 정답 FAQ가 있는 83문항, Recall@1:

| 종류 | n | 원문 그대로 | 핵심질문만 | 둘 합치기 |
|---|---|---|---|---|
| 긴 자연어 | 28 | **0.929** | 0.643 | 0.821 |
| 오탈자·띄어쓰기 | 20 | **0.900** | 0.900 | 0.900 |
| 대조쌍 | 16 | **0.750** | 0.750 | 0.750 |
| 후속·정정 | 19 | **0.526** | 0.368 | 0.421 |

→ **원문 검색이 모든 구간에서 가장 좋거나 같았습니다.** "긴 질문은 줄여서 찾자"는 가설은
측정에서 기각됐고, 핵심·조건 나누기는 **검색이 아니라 의도 판단·되묻기에만** 씁니다.
후속·정정 질문(0.526)만 별도 처리: 짧은 정정 문장은 앞 대화의 질문을 붙여 찾습니다.

## 10. LangChain을 실제 요청 경로에 올림 (2026-09-25 추가)

### 무엇이 문제였나

전에는 `CHAIN` 객체를 만들어 두고, 실제 요청은 같은 일을 손으로 다시 했습니다.
런타임에서 클래스를 감싸 세어 본 결과(상담 2건):

| | 전 | 후 |
|---|---|---|
| `RunnableSequence.invoke` | **0회** | **2회** (상담 1건에 1회) |
| `BaseRetriever.invoke` | 2회 | 2회 |
| `StructuredTool.invoke` | 1회 | 1회 |

즉 "질문 분석 → FAQ 검색 → 공식 조회 → 답변 생성이 하나의 체인"은 **말로만 맞고 코드로는
틀린 문장**이었습니다. 지금은 `support_chat_service.ask()`가 체인을 한 번 부르고,
답 쓰기까지 체인의 마지막 단계에서 일어납니다.

```
CHAIN = analyze_question | search_faq | decide_route | official_lookup | write_answer
          의도·조건        FaqRetriever   경로 5종      StructuredTool    ai_client
```

단계 시간은 체인 바깥의 타이머가 아니라 **LangChain 콜백**(`StageTimer`)에서 받습니다.
체인을 안 태우면 값이 아예 없으므로, 값이 있다는 것 자체가 체인이 돌았다는 증거입니다.
실제 상담 응답의 `trace.langchain`에 단계 이름과 호출 수가 그대로 남습니다.

### 곁따라 고쳐진 것 — FAQ 검색 중복

예전에는 경로 판단에서 한 번, 근거를 붙이려고 또 한 번 찾아 **질문 1건에 검색 2회**였습니다.
체인에서 검색을 한 단계로 만들면서 한 번으로 줄었습니다.

| 세트 | | 전(v5) | 후(v6) |
|---|---|---|---|
| final_v3 70문항 | 임베딩 호출 | 93 | **70** (문항당 1.0) |
| | 평균 처리 | 370.8 ms | **262.9 ms** |
| 회귀 150문항 | 임베딩 호출 | 177 | **150** (문항당 1.0) |
| | 평균 처리 | 284.1 ms | **217.7 ms** |

(AI는 stub이라 위 시간은 **우리 코드가 쓰는 시간**입니다. 실제 응답 시간은 여기에
AI 호출이 더해집니다 — 7절 참고.)

### 품질은 그대로인가 (바뀌었으면 개선이라고 못 씁니다)

| 지표 | 전(v5) | 후(v6) |

| 회귀 150문항 경로 준수율 | 0.833 | **0.833** |
| Recall@1 / @3 / @5 | 0.797 / 0.984 / 1.000 | **동일** |

**구조만 바꾸고 판정은 하나도 바꾸지 않았습니다.** 같은 질문에 같은 경로로 갑니다.
빨라진 것은 같은 검색을 두 번 하지 않게 된 만큼이고, 답의 정확성은 이 작업으로
좋아지지 않았습니다. 정확성은 여전히 **관세사 검토 전이라 미측정**입니다(9절).
